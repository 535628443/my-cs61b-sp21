------------------------------------------------------------
1. InsertRandomSpeedTest Results (String length L = 10)
------------------------------------------------------------
N = 10,000:
- ULLMap (Unordered Linked List Map): 0.29 sec
- MyHashMap: 0.01 sec
- Java's Built-in HashMap: 0.00 sec

N = 100,000:
- MyHashMap: 0.06 sec
- Java's Built-in HashMap: 0.03 sec

Observations:
- ULLMap scales as O(N^2) for insertion due to linear scanning of the entire list for each insert, quickly becoming prohibitively slow as N grows.
- MyHashMap achieves amortized O(1) constant time insertion due to effective hashing and dynamic resizing, performing within a factor of ~2x compared to Java's production-grade HashMap.

------------------------------------------------------------
2. InsertInOrderSpeedTest Results (Lexicographical order)
------------------------------------------------------------
N = 10,000:
- ULLMap: 0.55 sec
- MyHashMap: 0.01 sec
- Java's Built-in HashMap: 0.00 sec

N = 100,000:
- MyHashMap: 0.07 sec
- Java's Built-in HashMap: 0.04 sec

Observations:
- Unlike unbalanced BSTs (which degenerate to O(N^2) under in-order insertion), HashMaps distribute in-order keys pseudo-randomly across buckets, retaining high performance (near O(1) amortized) similar to random insertion.

3. BucketsSpeedTest Results (L = 10, N = 100,000)
------------------------------------------------------------
- MyHashMapALBuckets (ArrayList):     0.09 sec
- MyHashMapLLBuckets (LinkedList):    0.07 sec
- MyHashMapTSBuckets (TreeSet):       0.09 sec
- MyHashMapHSBuckets (HashSet):       0.10 sec
- MyHashMapPQBuckets (PriorityQueue): 0.09 sec

Observations:
- Across all five bucket data structure types, performance is virtually identical (~0.07s - 0.10s for 100,000 items).
- Because the load factor is maintained (<= 0.75), each bucket holds only a small constant number of items on average (typically 0 to 2 items), making the asymptotic differences between bucket data structures negligible in practice.

------------------------------------------------------------
4. Discussion Questions
------------------------------------------------------------
Q1: When would it be better to use a BSTMap / TreeMap instead of a HashMap?
Answer:
1. In-order Traversal: When keys must be stored in a sorted order, or when you need to iterate through keys in natural sorted order.
2. Range Queries & Nearest-Neighbor: When operations like finding all keys in a range [k1, k2], finding the minimum/maximum key, or finding the floor/ceiling key are required.
3. Poor Hash Functions: When keys do not have a well-distributed hashCode() implementation or are difficult to hash evenly, but can be compared (implement Comparable).
4. Deterministic Performance Guarantees: Self-balancing BSTs (like Red-Black trees) provide a strict worst-case time complexity of O(log N), whereas HashMaps can degenerate to O(N) worst-case if catastrophic hash collisions occur or during long resize pauses.

Q2: Would our hash table speed up if we were able to use a logarithmic search over the TreeSet or a constant-time search over the HashSet for buckets? Why or why not?
Answer:
No, it would not noticeably speed up. In a properly designed hash table with a uniform hash function and dynamic resizing (load factor <= 0.75), the average bucket size is very small (around 0 to 2 items). When searching over a collection with only 1 or 2 items, linear scanning (over LinkedList or ArrayList) requires only a couple of CPU instructions with zero extra memory overhead. In contrast, TreeSet (rebalancing tree nodes) and HashSet (secondary hashing and table overhead) introduce larger constant-factor costs. Therefore, asymptotic improvements within tiny buckets do not improve overall performance.
